# Authoring a new probe

This is the end-to-end tutorial for adding a new probe to NeMo UserSim. A
probe is a class with a handful of attributes and hooks: turn iteration, the
pre-filters, the judge gates, frustration escalation and early-stop all come
from the shared conversation loop. Every probe therefore gets the same
conversation semantics, and a fix to the loop reaches all of them at once.

For the substrate's API surface (every class, every mixin, every
hook), the source-of-truth docstrings live in
[`src/usersim/engine/core/probes.py`](../../src/usersim/engine/core/probes.py).
This file is the narrative companion: it tells you *which* substrate
piece to pick and *how* to wire it.

## Step 0: pick your shape

Use this decision tree to pick which substrate combination matches
your probe:

```
Does the probe have an asset bank (curated facts / queries / strategies / actions)?
│
├── NO → BaseProbe alone
│        Examples: general_open_ended, general_educational
│        Template: templates/probe/generator_baseprobe_only.py
│
└── YES → BankBackedProbe + mixin (depends on turn-1 shape)
         │
         ├── Turn-1 should be the bank's text VERBATIM
         │   (false-premise wording, exact phrasing for matched-pair joins,
         │    or reviewer-authored content must survive unchanged)
         │   │
         │   ├── Single back-and-forth conversation
         │   │   → BankVerbatimMixin
         │   │     Examples: sov_ai_facts, sov_ai_multilingual_parity
         │   │     Template: templates/probe/generator_bank_verbatim.py
         │   │
         │   ├── Multi-turn with bank-driven per-turn nudges (reframings)
         │   │   → BankReframingMixin
         │   │     Example: safety_chat_pressure
         │   │     Template: templates/probe/generator_bank_reframing.py
         │   │
         │   └── Single user turn + multi-assistant-turn tool loop
         │       (NO user-LLM at all; assistant tool-calls intercepted)
         │       → AgenticMixin (custom run_dispatch)
         │         Example: safety_agentic
         │         Template: templates/probe/generator_agentic.py
         │
         └── Turn-1 should be GENERATED by the user-LLM in the persona's
             voice, but ANCHORED to a bank-derived hint
             (paraphrasing through persona voice IS the feature)
             → BankBackedProbe, with the hint in the user system prompt
               Example: sov_ai_dynamic
               Template: templates/probe/generator_custom_turn1.py
             → or CustomTurn1InstructionMixin, when only turn 1 follows
               an instruction of its own
```

There's also a **tool-calling capability** shape (test the assistant's
ability to use user-provided tools, not safety-probe its tool use):
that's `BaseProbe + ToolCallingMixin`. Example: `tool_calling`. Template:
`templates/probe/generator_tool_calling.py`.

For probes that need an **inner assistant<->tool loop** (execute tool calls,
append `role:"tool"` results, re-call the assistant), inherit
`ToolExecutionMixin` and implement one `async execute_tool_call(name, args, tc,
state, models, *, turn_idx, call_idx) -> str` hook instead of hand-rolling
`after_assistant_turn`. It offers two modes via `tool_loop_mode`: `single`
(one round + synthesis, e.g. `tool_calling`) and `multi` (re-offer tools until
the assistant stops or a per-turn cap, e.g. `financial_services`). The
**grounded multi-turn + tool-loop** shape (multi-turn persona user-sim +
scoped retrieval + discoverable-tool gate + in-memory state, tier-branched) is
`financial_services`: it rides the shared `ConversationLoop` (no custom
`run_dispatch`) plus `ToolExecutionMixin`; the `dynamic` tier generates turn-1
from the shared `core/probing_taxonomy` substrate (`select_category`).

## Step 1: subclass `BaseProbe` + the right mixin

### MRO matters: mixin BEFORE the BaseProbe subclass

```python
# Correct: mixin first, BankBackedProbe second.
class MyProbe(BankVerbatimMixin, BankBackedProbe):
    ...

# WRONG: BankBackedProbe first hides the mixin's hook overrides.
class MyProbe(BankBackedProbe, BankVerbatimMixin):
    ...
```

The substrate's mixins exist to override `BaseProbe`'s sensible-default
hooks (`get_verbatim_first_user_turn` returns `None` by default;
`BankVerbatimMixin` doesn't itself override that (your probe does) but
future mixins may, and the convention keeps the MRO predictable).
Putting the mixin to the right of the base class would let
`BaseProbe`'s defaults win.

### What you must implement

`ProbeAdapter` has 8 required runtime hooks. `BaseProbe` supplies safe
defaults for five, so a new subclass implements the three marked required
below. `BankBackedProbe` adds 1 more (`derive_task`). Most are 1-line
implementations.

| Hook | Required? | Default | When you override |
|---|---|---|---|
| `label` (class attr) | yes | `<unset>` | Always set to `"my_probe"`. Must match `@register_probe(label=...)` |
| `get_user_system_prompt()` | yes | raises | Always |
| `get_assistant_system_prompt()` | yes | raises | Always: return `""` per pure-capability policy unless you have a research-grounded reason not to |
| `get_tools_for_assistant()` | no | `None` | When you expose tools (tool_calling, agentic) |
| `format_gate_prompt(user_query, history)` | no | generic rubric | When the gate needs probe-specific quality criteria |
| `format_assistant_judge_prompt(response, history)` | no | generic assistant-quality rubric | When the per-turn assistant judge needs probe-specific criteria; with `max_assistant_attempts > 1`, its verdict also gates resampling |
| `async after_assistant_turn(models, state, response, cfg)` | no | append + return content | When you intercept tool calls, simulate API responses, etc. Build the message with `assistant_message(response, content, tool_calls=..., store_reasoning=getattr(cfg, "store_reasoning", True))` from `core/probes.py` rather than a hand-written dict: it carries the model's `reasoning_content` (when there is one) onto the message it belongs to. A hand-built dict silently drops the trace, and for multi-call turns attributes it to the wrong message; omitting `store_reasoning` makes your probe ignore `--no-store-reasoning`. |
| `supports_assistant_resampling` (class attr) | no | `True` | Set `False` when `after_assistant_turn` has side effects (tool execution, multi-message appends): it caps judge-gated assistant resampling (`max_assistant_attempts > 1`) to one attempt. `ToolCallingMixin` / `AgenticMixin` already do this |
| `build_result_extras(state)` | no | num_turns + num_tool_calls | Always: surface the probe's join keys as top-level columns. **Every key you add here must also be listed in `ConversationSimulatorConfig.side_effect_columns`** -- see step 6 |
| `derive_task(persona, bank, *, cfg)` | yes (BankBacked only) | raises | Always for bank-backed probes |
| `async get_verbatim_first_user_turn(state)` | no | `None` | When turn-1 is verbatim from a bank: also seed metadata here |
| `get_user_query_instruction(turn_idx)` | no | `None` | When turn-1 is generated from an instruction of the probe's own: return it for `turn_idx=0`, and the loop hands it to the user-LLM in place of the standard one. `CustomTurn1InstructionMixin` fills it from a template. The draft still passes the gate |
| `seed_state_metadata(state)` | no | no-op | When you need to seed metadata path-agnostically (works for both verbatim and generate-and-gate) |
| `async format_followup_user_instructions(turn_idx, state)` | no | `[]` | When follow-up turns get bank-driven nudges (reframings) |
| `on_followup_failure(state, error_kind)` | no | `"skip"` | When gate exhaustion should ABORT the trajectory (safety_chat_pressure does this via `BankReframingMixin`) |
| `should_succeed(state)` | no | `True` | Always: assert your probe's join key is present |
| `should_inline_judge_user_turn(turn_idx, state)` | no | `True` | Rarely: `AgenticMixin` skips turn-0 |
| `should_inline_judge_assistant_turn(turn_idx, state)` | no | `True` | Rarely |
| `should_continue_after_turn(state)` | no | `True` | `AgenticMixin` returns False once assistant emits no tool calls |
| `allow_early_stop_at_turn(turn_idx, state)` | no | `True` | `ToolCallingMixin` defers until tools are used; `safety_chat_pressure` returns False (the dedicated capitulation classifier on the assistant side is the only stop signal) |
| `async is_capitulation_detected(state)` | no | `False` | `safety_chat_pressure` overrides this and runs a dedicated comparator-shaped classifier (`classifier.py::classify_capitulation`) against the assistant's last response. When True the simulator sets `stopped_on_capitulation=True`, `capitulated_at_turn=N`, emits `EARLY_STOP` + `CAPITULATION_CHECK` traces, and breaks the loop. Capitulation-specific by design: if a future probe needs a different post-assistant-turn stop reason, add a sibling hook with its own dedicated vocabulary rather than overloading this one. |
| `user_turn_policy()` | no | `UserTurnPolicy()`: the loop's own behaviour | When the probe tests what the model says across turns: turn off compression so the model sees its own replies, turn off the wrap-up anchor so every follow-up stays on topic, allow filter phrases its users naturally write, and skip names (such as brand names in Latin script) in the script check. `identity_disclosure` does all four. A generated opening can also be checked before the gate (`check_opening`): return why a draft breaks the probe's rules, and the loop asks for another draft within `max_query_attempts`. Read once per trajectory, after `derive_task` |
| `async run_dispatch(*, models, data, cfg)` | no | drives `ConversationLoop` | Only when the unified loop is wrong shape (currently: only `safety_agentic`) |

## Step 2: configure 2-3 class attributes

For `BankBackedProbe` subclasses:

```python
class MyProbe(BankVerbatimMixin, BankBackedProbe):
    label = "my_probe"                                          # required
    bank_loader = staticmethod(_my_bank_loader)                 # required
    placeholder_warning_kind = WarningKind.USED_PLACEHOLDER_FACT  # required
    bank_version_key: Optional[str] = None                      # default None = locale-keyed
```

`bank_version_key` is the **load-bearing config**:

- `None` (default): record `provenance.bank_version[<locale>]`. The
  inclusion convention: each locale has its own bank, downstream
  reporting reads per-locale.
- A string like `"safety"` or `"agentic"`: record
  `provenance.bank_version[<that_string>]`. The safety convention:
  bank is locale-independent (English-only), reporting reads under
  the stable string.

Get this wrong and the matching scorecard reads from the wrong key
and silently produces empty rollups.

For `BaseProbe`-only subclasses, just `label` is required.

## Step 3: wire the asset bank

(Skip this section if your probe is asset-free.)

### Bank loader contract

A bank loader is a callable that returns a bank object. The substrate
calls it with one positional argument (`locale`) first, falls back to
no-arg on `TypeError`. So:

- **Locale-keyed bank** (one file per locale): write
  `def loader(locale: str) -> Bank: ...`
- **Locale-independent bank** (one file shared): write
  `def loader() -> Bank: ...`

Both work via the same `bank_loader` slot.

### Module-level alias for test patchability

The substrate's `_load_bank_for_locale` calls `loader = type(self).bank_loader`.
If your tests want to monkeypatch the loader, point at a module-level
alias (not the class attr directly):

```python
# In your generator.py
from .bank import load_my_bank_default

_load_bank = load_my_bank_default  # tests patch this name


def _bank_loader(locale: str = "en_US"):
    return _load_bank(locale)


class MyProbe(BankVerbatimMixin, BankBackedProbe):
    bank_loader = staticmethod(_bank_loader)
```

Now `patch.object(probe_gen, "_load_bank", return_value=synth_bank)`
in tests intercepts at the module level: you don't need to know which
class attribute the substrate calls.

### The bank object contract

The substrate is duck-typed. Your bank just needs:

- `bank.bank_id: str`: for warning detail
- `bank.bank_version: str`: for `provenance.bank_version` pinning
- Whatever `derive_task` consumes

That's it. No required class hierarchy.

### `derive_task(persona, bank, *, cfg)` contract

Returns one task object (with at least `.id` and `.placeholder`)
or `None` if nothing matched. The substrate:

- Stores it on `self._task`.
- If `task.placeholder is True`, emits `placeholder_warning_kind`
  on the OutcomeBuilder.
- Pins `provenance.bank_version[bank_version_key or locale]`.

Your probe then reads `self._task` from the prompt-formatting hooks
and from `should_succeed` / `build_result_extras`.

## Step 4: write your `LocalePromptPack`

For ANY prompt that ships across multiple locales, use
`LocalePromptPack`. It validates at construction time that every locale
in `shipped_locales` has a prompt entry, half-shipped locales are
caught at import time, not at simulate-time when the locale's first
row trips a KeyError.

```python
from usersim.engine.core.probes import LocalePromptPack

MY_USER_PROMPTS = LocalePromptPack(
    label="my_probe.user_system",
    prompts={
        "en_US": "You are {persona}, a US user. Ask about {topic}.",
        "pt_BR": "Você é {persona}, um usuário brasileiro. Pergunte sobre {topic}.",
        "ja_JP": "あなたは{persona}、日本のユーザーです。{topic}について質問してください。",
        # ... rest of your shipped locales
    },
    shipped_locales=("en_US", "pt_BR", "ja_JP", "fr_FR", "hi_Deva_IN", "en_IN"),
)


# At simulate time:
prompt = MY_USER_PROMPTS.get(self._locale, persona="Sarah", topic="cooking")
```

If you only ship one locale (English-only safety probes do this),
plain string templates are fine: `LocalePromptPack` adds value
specifically for the half-shipped-locale failure mode.

## Step 5: write the user-judge gate prompt

The gate prompt asks an LLM judge whether each user turn is a
legitimate user message vs a role-violation / fourth-wall break /
off-topic content. The judge's PASS/FAIL determines whether the turn
is accepted or the loop retries.

`BaseProbe.format_gate_prompt` ships a generic role-violation rubric.
Override when the gate should be probe-grounded: every inclusion /
safety probe does, because the gate's "is this a real user turn"
question depends on knowing what the user is supposed to be doing.

```python
def format_gate_prompt(self, user_query: str, conversation_history: str) -> str:
    return MY_GATE_PROMPT_TEMPLATE.format(
        user_turn_to_evaluate=user_query,
        conversation_history=conversation_history,
        # Probe-specific anchors:
        topic=self._task.category,
        expected_question_type=self._task.question_type,
    )
```

The judge response must include `<rating>PASS</rating>` or
`<rating>FAIL</rating>`: `run_inline_judge` parses XML, not plain
text. If your prompt doesn't request that format, the judge will
return prose and the gate will fail-retry until exhausted.

## Step 6: `@register_probe`

```python
from usersim.engine.core.probes import register_probe


@register_probe(
    family="my_probe",         # PROBE_FAMILY constant
    prompt_version="v1.0",     # PROMPT_VERSION constant
    variants=("default",),     # PROBE_VARIANTS constant
)
class MyProbe(BankVerbatimMixin, BankBackedProbe):
    label = "my_probe"
    ...
```

The decorator does TWO things in one call:

1. Sets `PROBE_FAMILY` / `PROMPT_VERSION` / `PROBE_VARIANTS` on the
   class's MODULE (the smoke check reads them via
   `getattr(module, "PROBE_FAMILY", ...)`).
2. Adds the class to `_PROBE_REGISTRY` keyed by `cls.label`.

Both surfaces are what the dispatcher reads.

After this, you also need to import-trigger the registration in the
plugin's bootstrap. Add a line in
[`usersim/engine/generator.py::_bootstrap_probes`](../../src/usersim/engine/generator.py)
to import your module: that's what triggers the `@register_probe`
decorator at startup.

### Declare every column your probe writes

If `build_result_extras` adds a key, list it in `side_effect_columns` on
[`ConversationSimulatorConfig`](../../src/usersim/engine/config.py):

```python
# src/usersim/engine/config.py
@property
def side_effect_columns(self) -> list[str]:
    return [
        ...,
        "my_probe_task_id",   # the join key build_result_extras writes
    ]
```

The engine writes the configured column plus the names declared there and
discards everything else, without a warning. An undeclared key is computed
on every row, dropped on the way to storage, and then read back as absent
by your scorer -- which reports the trajectory as having nothing to score
rather than failing. A run like that looks entirely successful.

`tests/engine/test_plugin_entry_points.py` drives every registered probe
and fails on any column that is written but not declared, so this is
caught in CI rather than in a dataset.

## Step 7: run the smoke test

```bash
usersim smoke
```

Every check should report `[OK]`. Confirm your probe appears in the
`probe registry` line:

```
[OK]   probe registry        14 probe(s) registered: [..., 'my_probe', ...]
```

If your probe doesn't show up, the bootstrap import is the most
likely cause. If it shows up but `PROBE_FAMILY missing` fires, the
`@register_probe` decorator didn't run (check for an import-time
exception in your module).

## Worked example: a `cooking_advisor` probe end-to-end

Let's build a complete probe: `cooking_advisor` asks the assistant
for cooking help, with a curated bank of (cuisine × dietary
restriction) recipe-request templates. We'll use the
**banked-verbatim** shape because the bank's questions are
hand-authored and should reach the assistant unchanged.

### File 2: `src/usersim/engine/core/cooking_bank.py`

```python
"""Cooking-recipe bank loader."""

from __future__ import annotations

import os
from dataclasses import dataclass
from typing import Optional

import yaml

from usersim.engine.core._assets import probe_assets_dir


@dataclass
class CookingRecipe:
    id: str
    placeholder: bool
    cuisine: str
    dietary: str
    persona_tags: tuple[str, ...]
    question: str
    expected_themes: tuple[str, ...]


@dataclass
class CookingBank:
    bank_id: str
    bank_version: str
    placeholder: bool
    recipes: tuple[CookingRecipe, ...]

    def by_id(self, recipe_id: str) -> Optional[CookingRecipe]:
        return next((r for r in self.recipes if r.id == recipe_id), None)


_CACHE: dict[str, CookingBank] = {}


def load_cooking_bank_default() -> CookingBank:
    path = os.environ.get("USERSIM_COOKING_BANK") or str(
        probe_assets_dir("cooking_recipes") / "sample.yaml"
    )
    if path in _CACHE:
        return _CACHE[path]
    with open(path) as f:
        data = yaml.safe_load(f)
    bank = CookingBank(
        bank_id=data["bank_id"],
        bank_version=data["bank_version"],
        placeholder=data.get("placeholder", False),
        recipes=tuple(
            CookingRecipe(
                id=r["id"],
                placeholder=r.get("placeholder", False),
                cuisine=r["cuisine"],
                dietary=r["dietary"],
                persona_tags=tuple(r.get("persona_tags", [])),
                question=r["question"],
                expected_themes=tuple(r.get("expected_themes", [])),
            )
            for r in data["recipes"]
        ),
    )
    _CACHE[path] = bank
    return bank


def reset_cooking_bank_cache() -> None:
    _CACHE.clear()
```

### File 5: `src/usersim/engine/probes/cooking_advisor/generator.py`

```python
"""cooking_advisor probe: banked-verbatim recipe questions."""

from __future__ import annotations

from typing import Any, Optional

from usersim.engine.core.cooking_bank import (
    CookingRecipe, load_cooking_bank_default,
)
from usersim.engine.core.outcomes import WarningKind
from usersim.engine.core.probes import (
    BankBackedProbe, BankVerbatimMixin, register_probe,
)
from usersim.engine.probes.cooking_advisor.prompts import (
    COOKING_GATE_PROMPT, COOKING_USER_PROMPTS,
)

PROBE_FAMILY = "cooking_advisor"
PROBE_VARIANTS = ["default"]
PROMPT_VERSION = "v1.0"

_load_bank = load_cooking_bank_default


def _bank_loader():
    return _load_bank()


def should_succeed(state: Any) -> bool:
    return bool(state.metadata.get("recipe_id"))


@register_probe(
    family=PROBE_FAMILY,
    prompt_version=PROMPT_VERSION,
    variants=tuple(PROBE_VARIANTS),
)
class CookingAdvisorProbe(BankVerbatimMixin, BankBackedProbe):
    label = "cooking_advisor"
    bank_loader = staticmethod(_bank_loader)
    placeholder_warning_kind = WarningKind.USED_PLACEHOLDER_FACT
    bank_version_key = "cooking"  # locale-independent, this probe is en-only

    def derive_task(
        self, persona: dict, bank: Any, *, cfg: Any,
    ) -> Optional[CookingRecipe]:
        # Narrow by persona tags as the shipped probes do; this example
        # takes the first match.
        if not bank.recipes:
            return None
        return bank.recipes[0]

    def get_user_system_prompt(self) -> str:
        return COOKING_USER_PROMPTS.get(
            self._locale, persona=self._persona.get("first_name", "the user"),
        )

    def get_assistant_system_prompt(self) -> str:
        return ""  # Pure-capability-test policy.

    def format_gate_prompt(
        self, user_query: str, conversation_history: str,
    ) -> str:
        return COOKING_GATE_PROMPT.format(
            user_turn_to_evaluate=user_query,
            conversation_history=conversation_history,
        )

    async def get_verbatim_first_user_turn(self, state: Any) -> str:
        state.metadata["recipe_id"] = self._task.id
        state.metadata["cuisine"] = self._task.cuisine
        state.metadata["dietary"] = self._task.dietary
        state.metadata["bank_id"] = self._bank.bank_id
        state.metadata["bank_version"] = self._bank.bank_version
        return self._task.question

    def should_succeed(self, state: Any) -> bool:
        return should_succeed(state)

    def build_result_extras(self, state: Any) -> dict:
        extras = super().build_result_extras(state)
        if self._task is not None:
            extras["probe_variant"] = f"{self._task.cuisine}::{self._task.dietary}"
            extras["recipe_id"] = self._task.id
            extras["cuisine"] = self._task.cuisine
            extras["dietary"] = self._task.dietary
        return extras


# Optional thin shim for callers that import simulate_cooking_advisor.
async def simulate_cooking_advisor(
    models, data, persona, profile, locale, language, cfg, **kwargs,
):
    from usersim.engine.core.outcomes import OutcomeBuilder, Provenance
    provenance = kwargs.get("provenance") or Provenance()
    outcome_builder = kwargs.get("outcome_builder") or OutcomeBuilder(
        provenance=provenance,
    )
    probe = CookingAdvisorProbe(
        persona=persona, locale=locale, language=language, models=models,
        cfg=cfg, provenance=provenance, profile=profile, data=data,
        outcome_builder=outcome_builder,
    )
    return await probe.run_dispatch(models=models, data=data, cfg=cfg)
```

## Common gotchas

These eight points account for most first-run failures. Reading them before
you run the smoke test will save a cycle.
Read them before you run the smoke test.

### 1. Assistant system prompt must be empty (pure-capability policy)

Every probe ships `get_assistant_system_prompt() -> ""`. The assistant
under test gets NO system prompt: only conversation history (and
`tools=` parameter where applicable). Telling the model how to behave
contaminates the very signal each probe is designed to surface.

See [`docs/engine/README.md` "Assistant under test:
pure-capability policy"](README.md#assistant-under-test-pure-capability-policy)
for the full rationale. If your probe deliberately deviates, document
in the module docstring
entry. The default is empty; deviations are deliberate.

### 2. Test patching: BOTH `core.simulation.acall_llm` AND `core.judges.acall_llm`

Both modules locally re-import `acall_llm` from `core.llm` at module
load. Patching `core.llm.acall_llm` doesn't affect the imported
bindings. Use the `_patched_call_llm` context manager from the test
template, which patches both call sites at once:

```python
with patch(
    "usersim.engine.core.simulation.acall_llm",
    side_effect=side_effect,
), patch(
    "usersim.engine.core.judges.acall_llm",
    side_effect=side_effect,
):
    result = await probe_gen.simulate_my_probe(...)
```

### 3. Mock must be alias-dispatching with judge XML payloads

The loop calls user_model + judge_model + assistant_model in an order
that depends on probe shape and gate retries. A FIFO queue makes the
test brittle to internal refactors. Use the `_mock_call_llm` helper
that pops from the matching queue based on the alias kwarg.

Judge responses MUST include `<rating>PASS</rating>` or
`<rating>FAIL</rating>` XML: `run_inline_judge` in `core/judges.py`
parses XML, not plain text. Plain-text judge responses make the
gate fail-retry until exhausted, which then trips
`USER_QUERY_GATE_EXHAUSTED` failures that look like a probe bug
but are actually a test-fixture bug.

### 4. Mixin BEFORE the BaseProbe subclass in MRO

```python
# Correct: mixin first.
class MyProbe(BankVerbatimMixin, BankBackedProbe): ...

# WRONG: BaseProbe defaults win.
class MyProbe(BankBackedProbe, BankVerbatimMixin): ...
```

Python's MRO resolves left-to-right; mixin overrides need to come
first so they shadow `BaseProbe` defaults. Get this wrong and the
mixin's hooks silently never fire.

### 5. `@register_probe` sets module constants AND the registry entry

The decorator does both in one call. Don't manually set
`PROBE_FAMILY` / `PROMPT_VERSION` / `PROBE_VARIANTS` at module level
AND use the decorator: the decorator overwrites them. Pick one.
The decorator path is the recommended one (one source of truth, one
place to bump prompt_version).

### 6. `bank_version_key` controls where reporting reads the bank version

- `None` → `provenance.bank_version[<locale>]` (locale-keyed, the
  inclusion convention).
- `"safety"` / `"agentic"` / etc. → `provenance.bank_version["safety"]`
  (non-locale, the safety convention for English-only banks).

The matching scorer looks up under whichever key the probe pinned.
Mismatch = scorer reads None = silent rollup-zero. Choose the key
that matches your bank's locale topology and document the choice in
your probe module's docstring.

### 7. `derive_task` returning None must be handled in `__init__`

The substrate calls `derive_task(persona, bank, *, cfg)` and stores
the result on `self._task`. If `derive_task` returns `None` (no
matching asset), `self._task` is `None` and your prompt-formatting
hooks crash on `self._task.question`. Either:

- Override `__init__` to raise a `MyProbeError` after `super().__init__()`
  if `self._task is None`: the shim catches the exception and returns
  `SCENARIO_ABORTED`. (This is the canonical pattern; see every
  inclusion / safety probe.)
- Make every prompt-formatting hook tolerant of `self._task is None`
  and let `should_succeed` flag the failure. Less common because the
  trajectory still spends LLM calls.

### 8. Side-channel metadata seeding must survive failures

Pin `state.metadata["my_join_key"] = ...` BEFORE the first
assistant-LLM call, not after. Infrastructure failures (assistant
model raises, gate exhausts, etc.) finalize the trajectory in the
state it was in at the failure point: if you seeded after the
failed call, the side channels are missing on the FAILED row, and
matched-pair joins downstream silently drop those rows.

All asset-driven probes seed metadata in `get_verbatim_first_user_turn`
(verbatim path) or `seed_state_metadata` (path-agnostic): both fire
before any LLM call.

### 9. Hooks that reach a model must be `async def`

The loop awaits `get_verbatim_first_user_turn`,
`format_followup_user_instructions`, `after_assistant_turn`,
`is_capitulation_detected`, `execute_tool_call` and `run_dispatch`.
Declaring an override with a plain `def` registers fine and then raises
`TypeError` partway through a conversation, once the loop tries to await
whatever it returned. `usersim.testing.assert_probe_conforms` catches it
in your own test suite instead:

```python
from usersim.testing import assert_probe_conforms

def test_my_probe_conforms():
    assert_probe_conforms("my_probe")
```

## Test authoring

[`templates/probe/test_probe.py.template`](../../templates/probe/test_probe.py.template)
is the canonical scaffold. Copy it; substitute your probe's name;
fill in the 8 standard test stubs:

1. **Registry registration**: the probe label is in `_PROBE_REGISTRY` and
   resolves to a class, and `sys.modules[probe_cls.__module__]` exposes the
   three metadata constants.
2. **Single-turn end-to-end**: minimal mocked-LLM run produces a
   trajectory with `conversation_status=True`.
3. **First user turn shape** (verbatim probes only):
   `msgs[0]["content"] == bank.<your_task>.<verbatim_field>` exactly.
   Conversation messages are dicts, so index them rather than using
   attribute access.
4. **Two-turn follow-up**: provide 2 assistant responses, drive
   turn 2 via the user-agent + judge gate.
5. **`probe_variant` overridden**: assert `result["probe_variant"]`
   is the probe-specific value, not the registry default `"default"`.
6. **Placeholder warning emitted**: bank with `placeholder=True`
   triggers the warning kind on the outcome.
7. **Bank-load failure aborts cleanly**: env override pointed at a
   nonexistent file produces `SCENARIO_ABORTED`.
8. **No-matching-task aborts cleanly**: synthetic bank with
   persona-tag mismatch produces `SCENARIO_ABORTED` without any LLM
   calls.

Plus the **`should_succeed` invariant** test: the canonical pattern
is two assertions: empty-state returns False, populated-metadata
state returns True.

The test_probe_invariants.py file at the cross-probe level already
covers (1) for you parametrically. So your per-probe file can focus
on (2)-(8) plus the should_succeed contract: the cross-cutting
checks come for free.

For real working examples: `tests/engine/probes/test_sov_ai_facts.py`
(verbatim), `tests/engine/probes/test_safety_chat_pressure.py` (reframings and
abort policy), `tests/engine/probes/test_safety_agentic.py` (custom
run_dispatch and a simpler mock).

## Wiring the out-of-sim scorer

The probe simulator only PRODUCES trajectories. The matching scorer
that JUDGES the assistant's responses lives separately under
[`evaluator/scorers/<your_probe>.py`](../../src/usersim/engine/evaluator/scorers/).
This is the in-sim / out-of-sim boundary the architecture
deliberately enforces.

A scorer is a function `score_<your_probe>_trajectory(trajectory, models)`
returning a dict of axis scores and side-channel rollups. Register it at the
bottom of the module, the way every shipped scorer does:

```python
register_scorer("your_probe", score_your_probe_trajectory)
```

`register_scorer` takes the name and the function; it is not a decorator. The
`trajectory` argument carries every top-level column your
`build_result_extras` surfaced, because `TrajectoryEvaluatorGenerator` merges
the full row dict into it, so any side-channel column you set is visible.

Add the module path to
[`evaluator/scorers/__init__.py::DEFAULT_SCORER_MODULES`](../../src/usersim/engine/evaluator/scorers/__init__.py)
so the auto-load path picks it up. After that, `usersim eval` runs your scorer
for every trajectory whose `probe_family` matches your probe's label.

The scorer is its own design exercise (axis definition, rubric
authoring, threshold gating). See
[`evaluator/scorers/sov_ai_facts.py`](../../src/usersim/engine/evaluator/scorers/sov_ai_facts.py)
or `safety_chat_pressure.py` for canonical examples.
